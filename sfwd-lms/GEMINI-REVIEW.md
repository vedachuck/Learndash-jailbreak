# Gemini Code Review — LearnDash LMS 5.2.2 (Self-Hosted v3 Build)

**Review Date:** 23 October 2026  
**Target Build:** `learndash-lms-5.2.2-self-hosted-v3.zip`  
**Scope:** Self-hosted licensing/telemetry/updater neutralization (`ld-license.php`, `Status_Checker.php`, `Harbor/Provider.php`, `sfwd_lms.php`, `Support/Provider.php`) and Multi-Provider AI Architecture (`AI_Provider`, `AI_Provider_Factory`, `Anthropic`, `Gemini`, `OpenAI_Compatible`, `ChatGPT`, `Chat_Session`, `ChatGPT_Summarizer`, `class-ld-settings-section-ai-integrations.php`).

---

## Executive Summary

The `self-hosted v3` modifications are well-architected, surgical, and thoroughly documented in `SELF-HOSTED-CHANGES.md`. Specifically:
- **Harbor Licensing Neutralization:** Stopping `LearnDash\Core\Libraries\Harbor\Provider::configure()` before `LiquidWebHarbor::init()` and returning `[]` from `Status_Checker::get_legacy_license_keys()` completely closes the third-party update/phone-home vector introduced in LearnDash 5.1.0+.
- **Double Update Lock:** Combining `learndash_updates_enabled() => false` with `Update URI: learndash-self-hosted-build` in `sfwd_lms.php` prevents accidental overwrites from both LearnDash's updater and WordPress Core's plugin update checks.
- **Telemetry & TrustedLogin:** Cleanly unhooked, and the new guard in `class-ld-settings-section-telemetry.php` prevents fatal null-container errors on the Advanced Settings page.

During a line-by-line review of the modified PHP classes, **6 issues** were identified (2 high-priority functional API bugs, 3 security/hardening gaps, and 1 admin UX/performance cleanup). The drop-in replacement files accompanying this document resolve all 6 items.

## Detailed Findings & Reasoning for Fixes

### 1. OpenAI `gpt-5-mini` Parameter Incompatibility (`src/Core/Services/ChatGPT.php`)
* **Severity:** High (Functional Bug — HTTP 400 Error)
* **What Happened:** `ChatGPT::DEFAULT_MODEL` was updated from `gpt-3.5-turbo` to `gpt-5-mini`. However, `ChatGPT::send_command()` continued sending legacy completion parameters in the JSON body:
  ```php
  'max_tokens'  => self::MAX_TOKENS,
  'temperature' => self::TEMPERATURE, // 0.9
  'top_p'       => self::TOP_P,       // 0.7
  ```
* **Why It Breaks:** OpenAI's `gpt-5` family (`gpt-5`, `gpt-5-mini`, `gpt-5-nano`) and `o1`/`o3`/`o4` reasoning models reject `max_tokens` (requiring `max_completion_tokens` instead) and reject non-default `temperature` (`0.9`) and `top_p` (`0.7`) parameters with an `HTTP 400 Bad Request` error.
* **The Fix:** `ChatGPT::send_command()` now detects whether `$this->model` is a `gpt-5` or `o`-series reasoning model (`preg_match( '/^(gpt-5|o[134])/i', $this->model )`). When true, it sends `'max_completion_tokens' => self::MAX_TOKENS` and omits `temperature` and `top_p`. Legacy models (`gpt-4o`, `gpt-4o-mini`, `gpt-3.5-turbo`) continue receiving `max_tokens`, `temperature`, and `top_p`. Also added a filter to strip duplicate `ROLE_SYSTEM` messages in `ChatGPT::set_messages()` to match the other providers.

### 2. Strict Turn-Alternation & Initial Greeting Crash in Anthropic and Gemini (`Anthropic.php` & `Gemini.php`)
* **Severity:** High (Functional Bug — HTTP 400 Error on First Turn & Post-Summarization)
* **What Happened:**
  1. **First-Turn Failure:** When a new Virtual Instructor session starts, `Chat_Session::set_initial_message()` seeds `$this->messages` with an `AI_Provider::ROLE_ASSISTANT` greeting (`"Hello! My name is..."`). When the student sends their first question, `$this->messages` contains `[assistant, user]`. Anthropic's `/v1/messages` API strictly requires the first message in the `messages` array to have `"role": "user"`, immediately rejecting the request with `HTTP 400: messages: first message must use the "user" role`. Gemini's `generateContent` API enforces the same constraint (`user` must precede `model`).
  2. **Post-Summarization Failure:** When a long conversation triggers `construct_messages_from_command()`, it prepends a summary message with `AI_Provider::ROLE_USER` (`"Here is the summary of the previous conversation: ..."`) in front of `$summarizer->get_preserved_messages()` (the last 10 messages). If the first preserved message also has role `user`, or if the last preserved message has role `user` right before the new `$command` (`ROLE_USER`) is appended, the payload contains consecutive `user` messages (`[user, user]`), which both Anthropic and Gemini reject with an HTTP 400 role-alternation error.
* **The Fix:** Updated `map_messages_to_request_format()` in both `Anthropic.php` and `Gemini.php` to:
  1. Skip any leading `assistant`/`model` message before the first `user` message (since the greeting is static UI text generated by LearnDash, not needed as a prior turn before the user's first prompt).
  2. Automatically merge any consecutive messages that share the same role using `"\n\n"`, guaranteeing strict `user` ↔ `assistant`/`model` alternation under all summarization states.

### 3. Upstream Error Masking & Empty Response Handling in `ChatGPT.php` (`src/Core/Services/ChatGPT.php`)
* **Severity:** Medium (Security / Information Disclosure)
* **What Happened:** In `Anthropic.php`, `Gemini.php`, and `OpenAI_Compatible.php`, HTTP/API errors are written to `error_log()` while students see a generic message (`"The AI service is currently unavailable. Please try again later."`), and malformed API responses throw a `502` exception instead of returning an empty string. However, `ChatGPT.php` still threw raw upstream OpenAI error strings (which can leak account quota status or partial API key strings) directly to the student chatbox, and returned `''` on unexpected JSON shapes.
* **The Fix:** Updated `ChatGPT::request()` and `ChatGPT::send_command()` to log upstream errors via `error_log()`. If the call originates in `wp-admin` from an administrator (`is_admin() && current_user_can( LEARNDASH_ADMIN_CAPABILITY_CHECK )`), it still shows the detailed error so admins using the Course Outline or Quiz Creation tools can debug issues; on the frontend, students now receive the same generic error message as the other providers.

### 4. Short API Key Masking Leak (`includes/settings/settings-sections/class-ld-settings-section-ai-integrations.php`)
* **Severity:** Medium (Security — Credential Exposure in wp-admin HTML)
* **What Happened:** The `$mask_key` closure used:
  ```php
  $masked = Str::mask( $key, '*', 3, strlen( $key ) - 7 );
  return substr( $masked, 0, 35 ) . substr( $masked, -4, 4 );
  ```
  While OpenAI and Anthropic keys are 40+ characters, self-hosted `openai_compatible_api_key` values (e.g., for Ollama, vLLM, or local proxy tokens) are often short tokens (8–30 characters).
  - For keys with `strlen <= 10`, `strlen( $key ) - 7` leaves 7 characters unmasked (or passes a negative length if `< 7`).
  - For keys with `strlen <= 35`, `substr( $masked, 0, 35 )` returns the *entire* masked string (including the unmasked last 4 characters), and `. substr( $masked, -4, 4 )` **duplicates** the last 4 characters at the end.
* **The Fix:** Hardened `$mask_key` in `class-ld-settings-section-ai-integrations.php` to mask 100% of any key `<= 10` characters (`str_repeat( '*', $len )`), and only truncate + append the last 4 characters when `$len > 39`.

---

### 5. Empty/Invalid URL Guard in `OpenAI_Compatible` (`src/Core/Services/OpenAI_Compatible.php`)
* **Severity:** Low-Medium (Reliability / SSRF Hygiene)
* **What Happened:** If an admin selects `OpenAI-compatible / Self-hosted` as the provider but forgets to fill in `Server Base URL` (or enters a malformed URL), `$this->api_url` evaluated to `'chat/completions'`, causing `wp_remote_request()` to attempt an invalid relative HTTP call on every chat message.
* **The Fix:** Added a check in `OpenAI_Compatible::request()` verifying `! empty( $this->api_url ) && wp_http_validate_url( $this->api_url )` before invoking `wp_remote_request()`.

---

### 6. Admin Help Text Clarification & Harbor Hook Cleanup
* **Severity:** Low (UX & Performance)
* **What Happened:**
  1. In `class-ld-settings-section-ai-integrations.php`, the `ai_provider` dropdown help text stated: *"Select which AI service to use for Virtual Instructors, Course Outline generation, and Quiz Creation."* Because Course Outline and Quiz Creation are DI-wired specifically to `ChatGPT` (OpenAI), selecting Anthropic or Gemini there could confuse an admin when Quiz Creation still requires OpenAI.
  2. In `src/Core/Libraries/Harbor/Provider.php`, `register_actions()` still registered the `lw-harbor/legacy_licenses` filters and instantiated `new Addon_Legacy_Licenses(...)` on every single frontend and backend request, and ran `wp_clear_scheduled_hook( 'lw_harbor_data_refresh' )` unconditionally on `plugins_loaded` even when no cron was scheduled.
  3. In `src/Core/Services/Gemini.php`, a stale line in the class docblock still mentioned passing the API key as a URL query parameter.
* **The Fix:**
  - Updated the `ai_provider` label and help text in `class-ld-settings-section-ai-integrations.php` to clarify that the selector controls **Virtual Instructors**, while Course Outline and Quiz Creation require an OpenAI API key.
  - Simplified `Harbor\Provider::register_actions()` to only run on `admin_init` and only call `wp_clear_scheduled_hook()` if `wp_next_scheduled( 'lw_harbor_data_refresh' )` is truthy.
  - Cleaned up the stale docblock comment in `Gemini.php`.
